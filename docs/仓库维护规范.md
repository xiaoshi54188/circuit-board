# 仓库维护规范

## 一、目录布局

一个仓库、两个版本目录，每个目录都是一个能独立构建的 Gradle 工程：

```
circuit-board/
├─ README.md            对外说明（玩法、版本表、安装、构建）
├─ LICENSE              MIT
├─ CHANGELOG.md         按版本记录
├─ .gitignore           仓库级忽略规则，两个版本目录共用
├─ .github/ISSUE_TEMPLATE/{bug_report,crash_report,suggestion}.yml
├─ docs/                维护文档
├─ 1.21.1/              MC 1.21.1 + NeoForge 21.1.252（JDK 21，Gradle 8.12.1）
└─ 26.2/                MC 26.2 + NeoForge 26.2.0.76（JDK 25，Gradle 9.5.1）
```

每个版本目录内部：

```
├─ build.gradle
├─ settings.gradle
├─ gradle.properties        版本号、许可证、mod_id 等唯一配置源
├─ gradlew / gradlew.bat
├─ gradle/wrapper/          ★ 必须整套提交
└─ src/main/{java,resources}
```

## 二、该进库

| 类别 | 文件 | 为什么 |
| --- | --- | --- |
| 构建配置 | `build.gradle`、`settings.gradle`、`gradle.properties` | 克隆即可构建 |
| 构建引导 | `gradlew`、`gradlew.bat`、`gradle/wrapper/**` | 不依赖本机 Gradle 版本 |
| 源码 | `src/main/java/**` | 核心 |
| 资源 | `src/main/resources/{assets,data,META-INF,pack.mcmeta}` | 贴图、模型、配方、语言 |
| 元数据 | `README.md`、`LICENSE`、`CHANGELOG.md` | 门面 |
| 协作 | `.gitignore`、`.github/ISSUE_TEMPLATE` | 防脏文件、降低沟通成本 |
| 技术记录 | `1.21.1/PORTING.md` | 跨版本 API 差异，改代码时对照 |

## 三、不该进库

| 类别 | 例子 | 原因 |
| --- | --- | --- |
| 编译产物 | `build/`、`out/`、`classes/`、`*.jar` | 二进制，可由源码重建 |
| 构建缓存 | `.gradle/` | 上千缓存文件，纯噪音 |
| 运行残留 | `run/`、`logs/`、`crash-reports/` | 本地世界与日志，可能含隐私 |
| IDE 配置 | `.idea/*`、`*.iml`、`.settings/`、`.classpath` | 个人习惯，易冲突 |
| 本地依赖 | `libs/`、`mods/`、`flatdir/` | 他人 jar，无授权不应转存 |
| 凭据 | `*.jks`、`*.keystore`、`secrets.properties` | 泄露即事故 |

`.gitignore` 已覆盖以上全部。

## 四、版本号在哪里改

只改 `gradle.properties`，产物名（`archivesName`）和 `neoforge.mods.toml` 里的 `${mod_version}` 会跟着变；README 的版本表要手动同步。

- `mod_id=circuit_board`
- `mod_name` 当前是 `\u7ea2\u77f3\u7535\u8def\u753f`（红石电路板），这种 `\uXXXX` 转义是 Gradle properties 的兼容写法，别直接换成中文原文
- `mod_license=MIT`，和根目录 `LICENSE` 保持一致

## 五、发布节奏

- 源码进仓库，成品 jar 走 **Releases**，不要塞进源码树；
- tag 用 `<mc版本>-<mod版本>`，例如 `26.2-1.0.0`、`1.21.1-1.0.0`；
- 每次发布在 `CHANGELOG.md` 追加一段，不要只写在 commit message 里。
